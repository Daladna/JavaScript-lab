# Соответствие условию задания: где что реализовано

Для каждого пункта условия указано, в каких файлах и строках он выполнен.

> **Важно про номера строк.** Они указаны для файлов в том виде, в котором они были в первом архиве `afisha.zip` (до добавления PHPDoc). После добавления PHPDoc номера строк сдвинутся, поэтому рядом всегда указано **имя функции или метода**: по нему файл легко найти через поиск (Ctrl+F). В `Database.php` строки тоже могут немного отличаться, потому что вы правили этот файл под PHP 8.5.

Сокращения: `Ctrl.` — контроллер (`app/controllers/`), файлы моделей лежат в `app/models/`, шаблоны в `app/views/`.

## 1. Основные условия

| Условие | Как выполнено |
|---|---|
| Веб-приложение средней сложности с серверной логикой | Приложение «Афиша мероприятий»: вся логика на PHP (`app/`), данные в SQLite. Около 900 строк PHP-кода. |
| Любые frontend и backend технологии | Backend: PHP без фреймворков + PDO + SQLite. Frontend: HTML, CSS (`public/css/style.css`), JavaScript (`public/js/validate.js`). |
| Работа на GitHub, ссылка в Moodle | Делается вручную: загрузить папку `afisha` в репозиторий. Файл `afisha.sqlite` лучше в репозиторий не добавлять, он создаётся автоматически. |
| Индивидуальная работа | Выполнена как индивидуальная, один автор. |

**Проверка на стороне клиента** — `public/js/validate.js`:
- включается у форм с классом `js-validate` и атрибутом `novalidate`, стр. 4–5;
- `getMessage()`, стр. 7–33: обязательность, формат email, минимальная и максимальная длина, диапазон числа, совпадение паролей (стр. 26), дата не в прошлом (стр. 29);
- `showError()`, стр. 35–39: вывод сообщения под полем;
- обработчик отправки формы, стр. 41–: если есть ошибки, отправка отменяется.

Правила задаются атрибутами полей в шаблонах (`required`, `minlength`, `maxlength`, `min`, `max`, `data-match`, `data-future`).

**Проверка на стороне сервера** — `EventController.php`, метод `validate()`, стр. 113–178:
- название 3–100 символов (стр. 129–131), описание 10–2000 (135–137);
- категория существует в БД (141–143);
- дата в правильном формате и не в прошлом (147–153);
- место 2–150 символов (158–160), формат из списка (164), цена 0–100000 (168–170), возраст из списка (174).

Для регистрации и смены пароля серверная проверка находится в `User.php`: `validateNew()`, стр. 57–85, и `validatePassword()`, стр. 87–103.

**Обработка ошибок и понятные сообщения**
- Сообщения формируются в `validate()` и выводятся под каждым полем функцией `field_error()` (`helpers.php`, стр. 84). Эту же функцию использует `validate.js`, поэтому ошибки сервера и клиента выглядят одинаково.
- При ошибке форма показывается снова, введённые значения сохраняются (`$d` в `form.php`).
- Успех и ошибки действий выводятся сообщениями: `flash_set()` / `flash_get()` (`helpers.php`, стр. 33–44), показ в `layout/header.php`.
- Страницы ошибок 400, 403, 404: `abort()` (`helpers.php`, стр. 75), шаблон `error.php`.

## 3. Требования к безопасности

| Требование | Как выполнено | Файл и строки |
|---|---|---|
| Валидировать все введённые данные | Двойная проверка (JS + PHP) для всех форм. Параметры поиска проверяются при разборе `$_GET` | `validate.js`; `EventController.php`, `validate()` стр. 113–178 и `search()` стр. 7–23; `User.php`, стр. 57–103 |
| Защита от внедрения вредоносного кода (XSS) | Весь вывод экранируется `htmlspecialchars` через функцию `e()` | `helpers.php`, `e()`, стр. 14; применяется во всех шаблонах `app/views/` |
| Защита от внедрения SQL | Только подготовленные запросы PDO (`prepare` + `execute`), значения не склеиваются с SQL | все файлы моделей: `User.php`, `Event.php`, `Category.php` |
| Закрытые части защищены аутентификацией | Проверки `requireLogin()` и `requireAdmin()` в начале каждого защищённого действия | `Auth.php`, стр. 40–54; `AdminController.php`, стр. 5–8 |
| Пароли хранятся с безопасными хеш-функциями | bcrypt через `password_hash` / `password_verify` | `User.php`, стр. 38, 52; `AuthController.php`, стр. 39 |
| Сессии для управления доступом | В сессии хранится только `user_id`, пользователь и его роль каждый раз читаются из БД | `bootstrap.php`, стр. 17–18; `Auth.php`, метод `user()`, стр. 8–18 |
| Нельзя обойти аутентификацию | Права проверяются на сервере, а не только скрытием кнопок. Прямой переход по адресу закрытой страницы приводит к редиректу или ошибке 403 | `Auth.php`; `EventController::findOwn()` |
| Защита от фиксации сессии | `session_regenerate_id(true)` при входе и выходе | `Auth.php`, стр. 28 и 36 |
| Защита от подделки запросов (CSRF) | Скрытый токен в каждой POST-форме, проверка на сервере | `helpers.php`: `csrf_token()` стр. 46, `csrf_field()` стр. 54, `csrf_check()` стр. 59; вызывается во всех обработчиках POST |
| Cookie сессии | Флаги `httponly` и `samesite=Lax` | `bootstrap.php`, стр. 17 |
| Не подсказывать, существует ли email | Одинаковое сообщение «Неверный email или пароль» и одинаковый ответ при восстановлении | `AuthController.php`, стр. 44–45 и 87–88 |
| CAPTCHA (необязательно) | Не реализована, так как условием она только допускается | — |

## 5. Дополнительные требования к оформлению кода

Эти пункты не из исходного условия, а из ваших требований.

| Требование | Состояние |
|---|---|
| PHPDoc для каждой функции и метода (параметры, результат, функционал) | Добавляется через opencode по подготовленному промпту. После этого номера строк в этом документе сдвинутся, ориентируйтесь на имена методов |
| Понятные и информативные комментарии, без избыточных | В коде есть короткие комментарии только там, где логика неочевидна |
| Понятные имена переменных, функций и классов | Имена функций, методов и классов описательные. В некоторых местах остались однобуквенные переменные (`$s`, `$d`, `$f`, `$e`, `$u`). Если нужно, их можно переименовать отдельным промптом |
