# Афиша мероприятий — описание работы

Веб-приложение на «чистом» PHP (без фреймворков) с базой данных SQLite. Пользователи регистрируются, публикуют мероприятия, а все посетители могут искать их без входа. У администратора есть панель управления.

## 1. Как запустить

**Требования:** PHP 7.4+ (проверено на 8.3) с расширениями `pdo_sqlite` и `mbstring` (в XAMPP / OpenServer они включены по умолчанию). Папка `database/` должна быть доступна для записи.

**Вариант 1 — встроенный сервер PHP:**
```
cd afisha
php -S localhost:8000 -t public
```
Открыть в браузере: <http://localhost:8000>

**Вариант 2 — XAMPP / OpenServer:** скопировать папку `afisha` в `htdocs` и открыть `http://localhost/afisha/public/`.

База данных (`database/afisha.sqlite`) **создаётся автоматически** при первом запуске вместе с категориями, демо-мероприятиями и двумя пользователями. Устанавливать и настраивать ничего не нужно. Чтобы сбросить данные, достаточно удалить файл `afisha.sqlite`.

**Тестовые аккаунты:**

| Роль | Email | Пароль |
|---|---|---|
| Администратор | admin@example.com | admin123 |
| Пользователь | ivan@example.com | ivan12345 |

## 2. Структура проекта

```
afisha/
├── public/                 ← единственная папка, открытая для браузера
│   ├── index.php           ← точка входа, маршрутизация (?page=...)
│   ├── css/style.css
│   └── js/validate.js      ← клиентская валидация форм
├── app/
│   ├── config.php          ← настройки
│   ├── bootstrap.php       ← старт сессии, автозагрузка классов
│   ├── helpers.php         ← e(), redirect(), csrf, flash и т. п.
│   ├── core/               ← Database (подключение к БД), Auth (вход/роли)
│   ├── models/             ← User, Event, Category (работа с БД)
│   ├── controllers/        ← Home, Auth, Event, Admin (логика страниц)
│   └── views/              ← шаблоны страниц (HTML + PHP)
└── database/
    ├── schema.sql          ← структура таблиц
    └── afisha.sqlite       ← создаётся автоматически
```

Это архитектура **MVC**: модели работают с БД, контроллеры обрабатывают запросы, представления выводят HTML. Каждый запрос идёт через `public/index.php`, который по параметру `page` вызывает нужный метод контроллера.

## 3. База данных (4 таблицы)

- **users** — `id, username, email, password_hash, role ('user'/'admin'), created_at`
- **categories** — `id, name`
- **events** — `id, user_id, category_id, title, description, event_date, place, format, price, age_limit, created_at`
- **password_resets** — `id, user_id, token_hash, expires_at` (для восстановления пароля)

При удалении пользователя его мероприятия удаляются автоматически (`ON DELETE CASCADE`).

## 4. Как выполнены требования задания

### 4.1. Аутентификация
- **Регистрация** (`?page=register`) и **вход** (`?page=login`). После входа открываются защищённые разделы: «Мои мероприятия», «Добавить», для администратора — «Админ-панель».
- Пароли хранятся только в виде хеша: `password_hash()` при сохранении и `password_verify()` при входе (`app/models/User.php`, `AuthController.php`).
- **Доп. задание — восстановление пароля** (`?page=forgot` → `?page=reset`):
  1. Пользователь вводит email. Генерируется случайный токен (`random_bytes`), а в БД сохраняется только его **хеш** (SHA-256) и время жизни (1 час).
  2. Пользователю «отправляется» письмо со ссылкой. Письмо отправляется через `mail()` и **всегда записывается в `database/mail.log`**, так как на локальном сервере почта обычно не настроена.
  3. В **демо-режиме** (`show_reset_link` в `config.php`) ссылка дополнительно показывается на странице, чтобы можно было показать работу преподавателю. Для «боевого» режима поставьте `false`.
  4. По ссылке пользователь вводит новый пароль. После смены все токены этого пользователя удаляются, поэтому ссылка одноразовая.
  5. Ответ на странице одинаков и для существующего, и для несуществующего email, чтобы нельзя было узнать, зарегистрирован ли адрес.

### 4.2. Общедоступный компонент
Главная страница (`?page=home`) и страница поиска доступны без входа. На главной **три динамических блока**, данные берутся из БД:
1. «Ближайшие мероприятия» (6 ближайших по дате);
2. «Категории» с количеством мероприятий в каждой;
3. Статистика: число мероприятий и пользователей.

### 4.3. Формы
**Форма создания ресурса** (`?page=event_create`, она же используется для редактирования) — **8 полей** разных типов:

| Поле | Тип |
|---|---|
| Название | текстовое поле |
| Категория | выпадающий список |
| Дата и время | `datetime-local` |
| Место проведения | текстовое поле |
| Формат (очно / онлайн) | переключатель (radio) |
| Цена | число |
| Возрастное ограничение | выпадающий список |
| Описание | многострочное поле |

- **Проверка на клиенте** — `public/js/validate.js`: обязательность, длина, диапазон числа, формат email, совпадение паролей, дата не в прошлом. Ошибки показываются под полем красным текстом.
- **Проверка на сервере** — метод `EventController::validate()`: проверяет всё то же самое (и ещё то, что категория существует, а формат и возраст входят в допустимый список). Сервер не доверяет браузеру, поэтому проверка работает даже при отключённом JavaScript.
- **Ошибки:** при неверных данных форма показывается снова, введённые значения сохраняются, у каждого поля выводится понятное сообщение. Успешные действия подтверждаются зелёным сообщением.

**Форма поиска** (`?page=search`, публичная) — ищет по критериям: ключевое слово (название/описание), категория, формат, диапазон дат, максимальная цена. Поиск не зависит от регистра, в том числе для кириллицы.

В приложении есть и другие формы с валидацией: регистрация, вход, восстановление пароля, создание администратора.

### 4.4. Защищённый компонент и роль администратора
Доступ только после входа: «Мои мероприятия», создание, изменение и удаление **своих** мероприятий.

**Администратор** (`role = 'admin'`) получает **6 дополнительных функций** (`AdminController.php`):
1. Панель администратора (`?page=admin`);
2. Просмотр **всех** мероприятий всех пользователей;
3. Редактирование **любого** мероприятия;
4. Удаление **любого** мероприятия;
5. Просмотр списка пользователей;
6. Удаление пользователей (кроме самого себя) и **создание новых учётных записей с ролью администратора**.

Вместе с добавлением мероприятий это даёт полное управление данными: просмотр, добавление, редактирование и удаление.

## 5. Безопасность

| Угроза | Защита |
|---|---|
| Хранение паролей | `password_hash` / `password_verify` (bcrypt), в БД нет паролей в открытом виде |
| SQL-инъекции | везде **подготовленные запросы** PDO (`prepare` + `execute`) |
| XSS (внедрение кода) | весь вывод экранируется функцией `e()` (`htmlspecialchars`) |
| Обход аутентификации | доступ по **сессии**; `Auth::requireLogin()` и `Auth::requireAdmin()` вызываются в начале каждого защищённого действия |
| Права доступа | пользователь может менять только свои мероприятия, иначе ошибка 403; админ-страницы открыты только админам |
| Фиксация сессии | `session_regenerate_id(true)` при входе и выходе |
| CSRF (подделка запросов) | в каждой POST-форме скрытый токен, проверяется на сервере (`csrf_check()`) |
| Опасные действия по ссылке | удаление и выход выполняются только через POST |
| Перебор email | одинаковое сообщение «Неверный email или пароль» |
| Роль пользователя | роль читается из БД при каждом запросе, поэтому удалённый пользователь сразу теряет доступ |
| Доступ к файлам БД | в Apache папки `app/` и `database/` закрыты через `.htaccess`; браузеру открыта только `public/` |

## 6. Что проверено

Приложение протестировано автоматически (запросы curl к работающему серверу): регистрация и вход (в том числе с неверными данными); доступ к защищённым страницам без входа; создание, редактирование и удаление мероприятий; ошибки валидации на сервере; экранирование `<script>` в названии; чужие мероприятия недоступны (403); все функции администратора; запрет самоудаления; запрос без CSRF-токена (400); полный цикл восстановления пароля, включая повторное использование ссылки и смену пароля.

## 7. Что сказать на защите (кратко)

- Это MVC без фреймворка: `public/index.php` → контроллер → модель (SQLite через PDO) → представление.
- Два типа пользователей: обычный и администратор. Права проверяются на сервере, а не только скрытием кнопок.
- Валидация двойная: JS даёт быструю обратную связь, PHP — надёжную защиту.
- Пароли хешируются, токен восстановления хранится только в виде хеша и живёт один час.
